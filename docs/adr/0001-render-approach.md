# ADR 0001: 기본 렌더 방식은 CSS 2D `matrix()` 면(A′), 블록 200개 초과는 SVG(C)로 자동 전환

- 날짜: 2026-10-04 (독립 리뷰 2차 CONCERN 반영 후 재측정·개정)
- 카드: `iso-render-spike`
- 근거 데이터
  - [`bench/results.md`](../../bench/results.md): N = 50, 500, 1000, 2000, 방식 A·A′·B·C·D
    (재현 `SIZES=50,500,1000,2000 node bench/run.mjs`)
  - [`bench/results-threshold.md`](../../bench/results-threshold.md): N = 200, 300, 500, 700, 1000, 방식 A·A′·C
    (재현 `ONLY=A,A2,C SIZES=200,300,500,700,1000 OUT=results-threshold.md node bench/run.mjs`)
  - 분류기 검사: `node --test bench/classify.test.mjs`

## 상태

제안됨 (리뷰어 승인 전). 소유자는 "v0.1은 블록 수가 임계값을 넘으면 SVG(C) 경로로 자동 전환한다"를
이미 결정했다. 이 ADR은 그 임계값과 CSS 경로의 최적화(A′)를 측정값으로 정한다.

개정 이력: 1판(기본 A, 500개 초과 시 C)은 호버 지표가 틀려 BLOCK. 2판(기본 A, 200개 초과 시 C)은
FORKED 보고를 통째로 버린 분류와 호버만 잰 범위 때문에 CONCERN. 이 3판은 프레임 단위 합침 분류,
값 변경 패스, A′를 넣어 모든 수치를 다시 쟀다. 앞 판의 수치는 쓰지 않는다.

## 맥락

2.5d-ui는 크롬북 같은 저사양 기기에서 WebGL 없이 동작하는 등각 데이터 컴포넌트 라이브러리다.
같은 데이터·같은 격자·같은 호버(6px 들림, 180ms ease-out)로 다섯 방식을 구현했다(`bench/common.js`).

| 방식 | 구현 | 블록당 요소 | 값 변경 방식 |
| --- | --- | --- | --- |
| A | CSS 2D `matrix()` 면 3개 + 래퍼 (`bench/a-css2d.html`) | 4 | 등록된 `--h`(`@property`, `<number>`) 변경 + `transition: --h 0.18s` |
| A′ | A + `--x`·`--y`·`--i`를 `@property { inherits: false }`로 등록, 높이를 정수 px로 반올림 (`bench/a2-css2d-opt.html`) | 4 | A와 같음 |
| B | CSS 3D `preserve-3d` 큐브 (`bench/b-css3d.html`) | 4 | A와 같음 |
| C | JS로 좌표 계산 → SVG `polygon` 3개 (`bench/c-svg.html`) | 4 (`g` + `polygon` 3) | 180ms 보간, 프레임마다 모든 `points` 재작성 |
| D | Canvas 2D 전체 다시 그리기 (`bench/d-canvas.html`) | 0 | 180ms 보간, 프레임마다 전체 재그리기 |

C는 A와 블록당 요소 수가 같다. **C로 바꿔도 DOM 노드는 줄지 않는다.**

### 지표

- **첫 렌더**: 내비게이션 시작 → 모든 블록을 만든 뒤 double rAF의 `performance.mark`. 블록 50개에서도
  59.7–67.7ms(`bench/results.md`)이므로 대부분 블록 수와 무관한 고정 몫이다.
- **표시 프레임 드롭** (호버 1번 패스, 값 변경 3번 패스): cc `PipelineReporter`를 프레임
  (프로세스, `frame_source`, `frame_sequence`) 단위로 합친다. FORKED 사본도 포함하고, 한 프레임에
  `STATE_DROPPED`가 하나라도 있으면 드롭, 아니고 `STATE_PRESENTED_PARTIAL`이 하나라도 있으면 부분 갱신으로
  센다(`bench/classify.mjs`).
- **메인 스레드 프레임 누락** (호버 2번 패스): rAF 간격마다 놓친 vsync 수 max(0, round(간격/16.67) − 1)의
  합 / 기대 프레임 수.
- **부분 갱신은 예산 지표로 쓰지 않는다.** 합침 분류에서 부분 갱신은 "메인 스레드 몫이 같은 vsync에 들어오지
  못했다"는 지연 신호이고, 보이는 끊김과 다르다. 근거는 두 가지다.
  - D·500: 메인 스레드 누락 0.0%(rAF가 매 vsync 돌았다), 표시 드롭 2.3%인데 부분 갱신은 96.2%다.
  - 같은 A·500 호버 트레이스를 두 분류로 셌다. FORKED 제외 분류에서는 부분 갱신이 0%였고, 합침 분류에서는
    18.5–30.8%였다(옛 A 페이지와 새 A 페이지 각 2회, 일회성 확인이라 결과 파일에는 없다). 2판의 "부분
    갱신 0%"는 분류 방식 때문이었다.

  그래서 예산은 다음처럼 읽는다. 부분 갱신은 표에 참고로만 남긴다.
  - 호버: 표시 드롭 ≤ 5% **그리고** 메인 스레드 누락 ≤ 5%. 메인 스레드 누락은 새로 가리킨 블록이 늦게
    반응하는 정도를 나타낸다.
  - 값 변경: 표시 드롭 ≤ 5%. 값 변경 패스에서는 메인 스레드 지표를 재지 않았다.
- **값 변경 표본이 작다.** 한 번 바꾸고 되돌리는 동안 센 프레임은 11–54개다(B·2000이 11개). 28프레임이면 한 프레임이 3.6%이므로,
  5% 예산은 사실상 "드롭 1프레임 이하"다.

### 측정 조건과 한계

- **실제 크롬북이 아니다.** Apple M4 Pro 데스크톱에서 CDP `Emulation.setCPUThrottlingRate`(rate 6)로
  CPU만 6배 늦췄다. GPU·래스터는 늦추지 않았다. Chromium 153 headless, 1366×768, DPR 1. 방식×N마다 3회, 중앙값.
- 두 결과 파일은 따로 실행한 것이라 같은 칸이 다르다. 예를 들어 A′·500 첫 렌더는 127.8ms(`results.md`)와
  132.5ms(`results-threshold.md`), C·500 값 변경 드롭은 10.7%와 14.3%다. 임계값 판단에는
  `results-threshold.md`만 쓴다.
- DOM 네이티브 메모리는 재지 않았다. JS 힙은 모든 방식·N에서 1.13–1.53MB다.
- 실행 시간: `results.md` 849초, `results-threshold.md` 496초.

### A′ 최적화 효과

다른 팀은 실제 엘리먼트에서 500블록 첫 렌더가 약 200ms에서 약 85ms로 줄었다고 보고했다. **이 벤치에서는
그 크기가 재현되지 않았다.** 같은 실행 안에서 A → A′ 첫 렌더는 다음과 같다.

| N | `results.md` | `results-threshold.md` |
| ---: | --- | --- |
| 200 | — | 87.2 → 92.2 |
| 300 | — | 108.0 → 106.6 |
| 500 | 144.7 → 127.8 | 139.1 → 132.5 |
| 700 | — | 174.7 → 153.0 |
| 1000 | 221.4 → 180.1 | 228.2 → 178.6 |
| 2000 | 410.7 → 290.7 | — |

N이 클수록 효과가 커진다(1000에서 약 20%, 2000에서 약 29%). 500 이하에서는 실행 간 편차와 구분되지 않는다.
벤치 A에는 라벨·접근성 표 등이 없어 실제 엘리먼트와 구성이 다르다. 그 차이가 원인인지는 **조사하지 않았다.**
호버와 값 변경에서는 A와 A′의 차이가 없다.

## 결정

1. **CSS 경로는 A′로 구현한다.** 측정한 모든 지표에서 A보다 나쁘지 않고, 블록이 많을수록 첫 렌더가 빠르다
   (표 S1·S2). 높이를 정수 px로 반올림해 생기는 오차(≤ 0.5px)는 받아들인다.
2. **자동 전환 임계값은 블록 200개다.** 200개 이하는 A′, 넘으면 C를 쓴다.
   - A′가 첫 렌더 예산(≤ 100ms)을 지키는 마지막 측정점은 200개(92.2ms)다. 300개에서는 106.6ms로 넘는다.
   - 같은 구간에서 C는 71.8ms, 86.1ms로 예산을 지킨다.
   - A′의 호버는 500개까지 예산을 지키고, 700개에서 메인 스레드 누락 6.7%로 넘는다. 그러므로 임계값을 정하는
     것은 첫 렌더다.
   - 200과 300 사이는 재지 않았다. 200은 잰 점 가운데 안전한 쪽이다.
3. **C 경로는 1000개까지 지원한다.** C는 1000개에서 호버 예산을 지킨다(표시 드롭 0.8%, 메인 스레드 누락 0.0%).
   첫 렌더는 700개 96.1ms, 1000개 105.6ms다. 1000개를 넘는 장면도 C로 그리지만 예산은 보장하지 않는다.
   2000개 C의 메인 스레드 누락은 10.4%다(`results.md`).
4. **B는 쓰지 않는다.** 500개에서 호버 표시 드롭 30.7%, 메인 스레드 누락 44.9%다.
5. **D로 대체하지 않는다.** 1000개에서 호버 표시 드롭 36.8%, C는 1.6%다(`results.md`). D가 이기는 곳은
   1000개 이상의 첫 렌더와 값 변경 드롭(1000개 40.0% vs C 54.8%)뿐이며, 둘 다 예산 안에 들지 못한다.

### 성능 예산 대비 (결정한 경로: N ≤ 200 A′, 200 < N ≤ 1000 C)

| 예산 (`docs/plan.html`) | 결과 | 근거 |
| --- | --- | --- |
| 유휴 CPU 0% | **충족** | 모든 방식·N에서 rAF 0, Paint 0 |
| 호버 60fps: 표시 드롭 ≤ 5%, 메인 스레드 누락 ≤ 5% | **N ≤ 1000에서 충족** | A′·50: 0.8% / 0.0%, A′·200: 0.0% / 0.0%. C 300–1000: 표시 드롭 최대 0.8%, 메인 스레드 누락 0.0% |
| 값 변경 애니메이션: 표시 드롭 ≤ 5% | **미달 (N = 50의 C만 충족)** | A′·50 8.3%, A′·200 66.7%. C·200 7.1%, C·500 14.3%, C·1000 54.8% |
| 블록 500개 첫 렌더 ≤ 100ms | **충족 (C 경로)** | C·500 86.9ms. A′였다면 132.5ms |
| 추가 메모리 ≤ 5MB | **JS 힙만 충족, DOM 미측정** | JS 힙 1.13–1.53MB |

**값 변경 예산은 v0.1에서 지키지 못한다. 소유자 결정이 필요하다.** 수치는 다음과 같다.

- A′의 등록된 `--h` 트랜지션은 블록 50개에서도 8.3%(24프레임 중 2), 200개에서 66.7%를 드롭한다.
- 같은 N에서 C의 JS 보간은 0.0%, 7.1%다. 값 변경만 보면 측정한 모든 N에서 C가 A′보다 낫다.
- 고를 수 있는 길은 셋이다.
  - (가) v0.1에서는 값 변경 미달을 알려진 한계로 받아들이고 임계값 200을 유지한다.
  - (나) 임계값을 더 낮춰 C의 범위를 넓힌다. 다만 C도 200개에서 7.1%라 예산 안에 들지 못한다.
  - (다) CSS 경로의 높이 애니메이션 방식을 바꾸는 후속 카드를 만든다. 대안의 효과는 **측정하지 않았다.**
- 이 ADR은 (가)를 제안한다. 임계값은 측정으로 근거를 댈 수 있는 첫 렌더·호버로 정했다.

## 결과

- 코어 CSS(`iso-core-primitives`)는 A′의 두 가지 최적화를 적용한다. `packages/core/API.md`의 `--iso-x`,
  `--iso-y`, `--iso-z`를 `@property { inherits: false }`로 등록하고, 높이를 정수 px로 반올림한다.
  API 문서에서 이 변수들의 상속 여부를 고치는 일은 해당 카드가 맡는다.
- 엘리먼트는 렌더 전에 블록 수를 세어 200을 넘으면 C 경로를 쓴다. C 경로 구현은 별도 카드로 lead가 배치한다.
- `docs/plan.html`의 호버 예산은 "표시 드롭 ≤ 5%, 메인 스레드 누락 ≤ 5%(블록 1000개 이하)"로 고쳤다.
  값 변경 예산은 따로 적고 미달이라고 표시했다.
- 이 결정은 CPU만 늦춘 데스크톱 측정에 기대고 있다. 실제 크롬북(ChromeOS Chrome 120+)에서 A′·200,
  C·300, C·1000의 첫 렌더·호버·값 변경을 다시 재서, 결과가 다르면 이 ADR을 대체하는 새 ADR을 쓴다.

2. **City4Age**는 노인의 경도인지장애와 노쇠를 조기에 발견하는 EU Horizon 2020 연구 프로젝트로, 코드 시각화와 관계없다. **CodeCity**(Wettel, Lanza)는 클래스를 건물로, 패키지를 구역으로 나타내는 3D 시각화 도구다. https://www.inf.usi.ch/lanza/PUBS/P/Wett2008a.pdf
3. 근거를 찾지 못했다. WebGL Fundamentals는 Chrome에서 컨텍스트 자체의 고정 오버헤드를 2–4MB로 설명하고, 나머지는 캔버스 크기와 버퍼 설정에 비례한다고 한다. 이 ADR의 논거에 쓰지 않는다. https://webglfundamentals.org/webgl/lessons/webgl-qna-why-does-webgl-take-more-memory-than-canvas-2d.html
4. **Isomer**(`jdan/isomer`)는 마지막 커밋이 2017-07이다. **Obelisk.js**(`nosir/obelisk.js`)는 마지막 커밋이 2019-06이다. 둘 다 Canvas 2D 도형 엔진이고 데이터 바인딩이 없다.
5. 가장 가까운 사례는 다음과 같다.
   - `isometric-css`, `@elchininet/isometric`: 유지보수 중이지만 투영을 도와주는 도구다.
   - PolyCSS: 메시 렌더러다.
   - ECharts-GL: WebGL 기반이다.
   - Recharts, Nivo, visx: 2D만 지원한다.
   검색 범위가 키워드 검색이라 "없다"를 증명한 것은 아니다.
6. Tailwind 공식 문서에 `transform-3d`, `rotate-x-*`, `rotate-y-*`, `translate-z-*`, `perspective-*`, `backface-hidden`이 있다. 모두 `preserve-3d` 계열이라 이 ADR이 기각한 B안에 해당한다. https://tailwindcss.com/docs/perspective
7. `pmndrs/uikit`의 코어 `@pmndrs/uikit`이 `yoga-layout`에 의존한다. WebGL 기반이라 비교 대상일 뿐 선행 사례는 아니다. https://github.com/pmndrs/uikit

**결론:** 데이터를 바인딩하고 WebGL을 쓰지 않는 2.5D 컴포넌트 라이브러리는 이번 검색 범위에서는 찾지 못했다. 따라서 전제는 유지한다. City4Age 사례와 "WebGL 80–200MB" 수치는 근거로 쓰지 않는다.
