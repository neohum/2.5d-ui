# ADR 0001: 기본 렌더 방식은 CSS 2D `matrix()` 면, 블록 200개 초과는 SVG

- 날짜: 2026-10-04 (독립 리뷰 BLOCK 반영 후 재측정·개정)
- 카드: `iso-render-spike`
- 근거 데이터: [`bench/results.md`](../../bench/results.md) 표 1(N = 50, 500, 1000, 2000, 네 방식)과
  [`bench/results-threshold.md`](../../bench/results-threshold.md) 표 1(N = 100–400, A·C만).
  재현: `node bench/run.mjs`, `ONLY=A,C SIZES=100,200,300,400 OUT=results-threshold.md node bench/run.mjs`

## 상태

제안됨 (리뷰어 승인 전). 첫 판(기본 A, 500개 초과 시 C)은 호버 지표가 틀려 독립 리뷰에서
BLOCK됐다. 이 판은 지표와 D 구현을 고친 뒤 다시 잰 값만 쓴다.

## 맥락

2.5d-ui는 크롬북 같은 저사양 기기에서 WebGL 없이 동작하는 등각 데이터 컴포넌트 라이브러리다.
`docs/plan.html`은 "CSS 2D `matrix()` 면 3개(A)"를 기본 가설로 두고, 아래 네 방식을 같은 데이터로
재서 고르기로 했다.

| 방식 | 구현 | 블록당 요소 |
| --- | --- | --- |
| A | CSS 2D `matrix()` 면 3개 + 래퍼 (`bench/a-css2d.html`) | 4 (`div` + `i` 3) |
| B | CSS 3D `preserve-3d` 큐브 (`bench/b-css3d.html`) | 4 (`div` + `i` 3) |
| C | JS로 좌표 계산 → SVG `polygon` 3개 (`bench/c-svg.html`) | 4 (`g` + `polygon` 3) |
| D | Canvas 2D 전체 다시 그리기 (`bench/d-canvas.html`) | 0 |

C는 A와 블록당 요소 수가 같다(N = 500에서 A 2009, C 2008). **C로 바꿔도 DOM 노드는 줄지 않는다.**

네 방식 모두 같은 모듈(`bench/common.js`)에서 시드 고정 높이로 같은 격자를 만들고, 화면 결과가
같은지 스크린샷으로 확인했다. 호버하면 블록이 6px 들린다. A·B·C는 CSS `transition: transform
0.18s ease-out`, D는 블록마다 따로 같은 180ms ease-out으로 올리고 내린다(첫 판의 D는 이전 블록을
즉시 내려서 작업량이 달랐다. 고쳤다).

### 호버 지표 (첫 판에서 바꾼 것)

첫 판의 "호버 프레임 드롭"은 rAF 간격 중 20ms를 넘는 비율이었다. 이 값은 놓친 프레임 수가 아니고
(33.3ms 간격이 이어지면 실제로는 50%인데 100%로 나온다), 메인 스레드 지연일 뿐 화면에 표시된 프레임
손실도 아니다. CSS transform 트랜지션은 컴포지터에서 돌기 때문이다. 이번에는 같은 페이지에서
두 패스를 따로 돈다.

- **표시 프레임 드롭 / 부분 갱신** (컴포지터, rAF 탐침 없음): cc `PipelineReporter`의
  `frame_reporter.state`. 드롭 = `STATE_DROPPED`, 부분 갱신 = `STATE_PRESENTED_PARTIAL`(화면은
  갱신됐지만 늦은 메인 스레드 몫, 예를 들어 새 호버 상태 반영이 빠진 프레임). FORKED 사본과
  업데이트가 필요 없던 프레임은 분모에서 뺀다.
- **메인 스레드 프레임 누락** (rAF 탐침): Σ max(0, round(간격 / 16.67) − 1) / (창 길이 / 16.67).

이 ADR은 호버 예산 "프레임 드랍 ≤ 5%"를 **표시 프레임 드롭 ≤ 5% 그리고 부분 갱신 ≤ 5%**로 읽는다.
부분 갱신을 넣는 까닭은 A의 결과 때문이다. A는 2000블록에서도 표시 프레임 드롭이 1.6%지만, 부분 갱신이
71.3%다. 이미 시작한 들림 애니메이션은 매끄럽지만, 새로 가리킨 블록이 늦게 반응한다는 뜻이다.

### 측정 조건과 한계

- **실제 크롬북이 아니다.** Apple M4 Pro 데스크톱에서 CDP `Emulation.setCPUThrottlingRate`(rate 6)로
  CPU만 6배 늦췄다. GPU·래스터·메모리 대역폭은 늦춰지지 않으므로 B(합성)와 D(캔버스 래스터)는
  실기기에서 이 표보다 나쁠 수 있다. 컴포지터 지표도 실기기 GPU에서는 달라질 수 있다.
- Chromium 153 headless, 1366×768, DPR 1. 방식×N마다 3회, 중앙값.
- 첫 렌더는 내비게이션 시작부터 잰다. 블록 50개에서도 56.8–63.0ms가 나오므로, 이 가운데 대부분은
  블록 수와 무관한 내비게이션·모듈 로드 몫이다.
- 첫 판과 이번 판 사이에 같은 조건의 C·2000 첫 렌더가 193.4 / 153.3 / 159.1ms로 달랐다.
  실행 간 편차가 20% 안팎이므로 수십 ms 차이로는 결론을 내리지 않는다.
- JS 힙(1.12–1.44MB)은 방식 간 차이가 거의 없다. DOM 노드의 네이티브 메모리는 JS 힙에 잡히지
  않으며 **측정하지 않았다.**
- `bench/results.md` 전체 실행은 593초 걸렸다(목표 약 5분 초과). B의 호버 패스가 메인 스레드를
  막아 마우스 이동이 밀린 탓이다(B·2000 표시 프레임 1134개 ≈ 19초).

## 결정

1. **기본 렌더 방식은 A(CSS 2D `matrix()` 면)다. 단, 한 장면의 블록이 200개 이하일 때만 쓴다.**
   - A가 계획서의 성능 예산을 모두 만족하는 구간은 N ≤ 200이다. 200블록 첫 렌더는 82.5ms(≤ 100ms),
     표시 프레임 드롭 0.0%, 부분 갱신 0.8%, 유휴 활동 0이다. 300블록부터 첫 렌더가 109.9ms로 예산을
     넘는다.
   - JS 없이 CSS만으로 쓸 수 있고, 텍스트·이벤트·접근성이 일반 DOM 그대로다. `packages/core/API.md`의
     CSS 프리미티브 계약(2D `matrix()`만 사용)과 일치한다. 현재 엘리먼트가 그리는 블록 수는 대부분 이
     범위 안이다(막대·적층·KPI는 수십 개, 7×24 히트맵은 168개).
   - 첫 판의 "500개까지 A"는 철회한다. A는 500블록에서 호버 예산은 지키지만(0.0% / 0.0%), 첫 렌더가
     133.4ms로 예산(블록 500개 ≤ 100ms)을 넘는다.
2. **블록이 200개를 넘으면 C(SVG `polygon`)로 바꾼다.** 이유는 DOM 노드 수가 아니라(C도 블록당
   요소 4개) 아래 두 가지다.
   - **첫 렌더**: C는 500블록에서 83.2ms로 예산을 지킨다(A 133.4ms).
   - **부하 속 호버 반응**: 1000블록에서 C는 부분 갱신 0.8%, 메인 스레드 누락 0.0%다. A는 각각
     39.1%, 30.4%로, 새로 가리킨 블록의 반응이 늦다.
3. **B(CSS 3D `preserve-3d`)는 쓰지 않는다.** 500블록에서 표시 프레임 드롭 30.9%로 예산을 크게 넘고,
   2000블록 첫 렌더가 가장 느리다(506.0ms). GPU를 늦추지 않은 조건에서도 이렇다.
4. **D(Canvas)로 대체하는 것은 데이터가 정당화하지 않는다.** A·B·C와 같은 독립 트랜지션 작업량으로
   고친 뒤에도 D는 1000블록에서 표시 프레임 드롭 38.6%, 2000에서 63.8%다. 같은 N에서 C는 0.0%다.
   D가 이기는 곳은 1000·2000블록 첫 렌더(95.6 / 127.0ms vs C 106.7 / 159.1ms)와 DOM 노드 수뿐이며,
   첫 렌더 차이는 실행 간 편차 범위에 가깝다. D 대체 임계값은 정하지 않는다.
5. **지원 상한은 블록 1000개로 둔다.** 2000블록에서 예산을 지킨 방식이 없다. C는 표시 프레임 드롭
   0.0%지만 부분 갱신 15.5%, 메인 스레드 누락 7.4%로 예산을 넘는다. 1000개를 넘는 장면도 C로
   그리지만 성능 예산을 보장하지 않는다고 문서에 적는다.

### 성능 예산 대비 (결정한 경로 기준)

| 예산 (`docs/plan.html`) | 결과 | 근거 |
| --- | --- | --- |
| 유휴 CPU 0% (10초 트레이스, 스크립트·페인트 0건) | **충족** | 모든 방식·N에서 rAF 0, Paint 0 |
| 호버 60fps, 프레임 드랍 ≤ 5% (표시 드롭·부분 갱신으로 읽음) | **N ≤ 1000에서 충족, 2000에서 미달** | A ≤ 200: 최대 0.8%. C 300–1000: 최대 0.8%. C 2000: 부분 갱신 15.5% |
| 블록 500개 첫 렌더 ≤ 100ms | **충족 (C 경로)** | C·500 83.2ms. A였다면 133.4ms로 미달 |
| 추가 메모리 ≤ 5MB (JS 힙 + DOM) | **JS 힙만 충족, DOM 미측정** | JS 힙 1.12–1.44MB. DOM 네이티브 메모리는 재지 않음 |

예산 문구 변경 제안(`docs/plan.html`에 반영):

- 호버 예산의 "프레임 드랍"을 "표시 프레임 드롭 ≤ 5%, 부분 갱신 ≤ 5% (`PipelineReporter`)"로 못박는다.
  메인 스레드 누락은 참고값으로만 적는다.
- 호버 예산의 적용 범위를 "블록 1000개 이하"로 적는다. 2000블록은 v0.1에서 예산 밖이다.
- 첫 렌더 예산은 그대로 둔다(블록 500개 ≤ 100ms). 내비게이션부터 재므로 블록 50개에서 56.8–63.0ms인 고정 몫이
  들어 있다는 점을 측정 방법에 적는다.

## 결과

- 코어 CSS(`iso-core-primitives`)와 엘리먼트 카드는 A를 그대로 구현한다. API 계약 변경은 없다.
- 엘리먼트는 렌더 전에 블록 수를 세어 200을 넘으면 C 경로를 쓴다. C는 JS가 필요하지만 Web
  Components는 이미 JS로 동작하므로 새 의존성은 없다. CSS만 쓰는 사용자는 200블록을 넘는 장면에서
  성능 예산을 보장받지 못한다는 점을 문서에 적는다. C 경로 구현은 별도 카드로 lead가 배치한다.
- C 경로는 블록 수를 줄이지 않는다. DOM 노드가 문제가 되는 상황(예: 메모리)은 이번 데이터로
  해결되지 않으며, DOM 네이티브 메모리를 재는 후속 측정이 필요하다.
- 200과 300 사이, 1000과 2000 사이는 재지 않았다. 임계값 200과 상한 1000은 잰 점 가운데 안전한
  쪽을 고른 값이다.
- D의 결과는 이번 구현 방식(움직이는 블록이 있는 동안 매 프레임 전체를 다시 그리고, `mousemove`마다
  모든 블록을 히트 테스트)의 결과다. 바뀐 영역만 다시 그리는 구현이 나아질 수는 있지만 **측정하지
  않았다.** D를 다시 검토하려면 그 구현으로 `bench/d-canvas.html`을 바꾸고 1000·2000블록 표시 프레임
  드롭이 C 이하임을 보여야 한다.
- 이 결정은 CPU만 늦춘 데스크톱 측정에 기대고 있다. 실제 크롬북(ChromeOS Chrome 120+)에서 A·200,
  C·500, C·1000을 다시 재서 결과가 다르면, 이 ADR을 대체하는 새 ADR을 쓴다.

   검색 범위가 키워드 검색이라 "없다"를 증명한 것은 아니다.
6. Tailwind 공식 문서에 `transform-3d`, `rotate-x-*`, `rotate-y-*`, `translate-z-*`, `perspective-*`, `backface-hidden`이 있다. 모두 `preserve-3d` 계열이라 이 ADR이 기각한 B안에 해당한다. https://tailwindcss.com/docs/perspective
7. `pmndrs/uikit`의 코어 `@pmndrs/uikit`이 `yoga-layout`에 의존한다. WebGL 기반이라 비교 대상일 뿐 선행 사례는 아니다. https://github.com/pmndrs/uikit

**결론:** 데이터를 바인딩하고 WebGL을 쓰지 않는 2.5D 컴포넌트 라이브러리는 이번 검색 범위에서는 찾지 못했다. 따라서 전제는 유지한다. City4Age 사례와 "WebGL 80–200MB" 수치는 근거로 쓰지 않는다.
