2.5d-ui 구축 계획

크롬북 같은 저사양 기기에서 WebGL 없이 CSS만으로 동작하는, 데이터 표현용 등각(아이소메트릭) 2.5D 컴포넌트 라이브러리를 만든다.

저장소 2.5d-ui대상 런타임 ChromeOS Chrome 120+상태 승인 · 라이선스 MIT
배경

왜 만드는가

지금은 데이터 시각화 라이브러리(D3, ECharts, Recharts)와 3D 라이브러리(Three.js, Spline) 사이가 비어 있다. 2D 차트는 계층·누적·부피를 표현하는 데 한계가 있다. 3D 차트는 WebGL 스택을 통째로 가져오기 때문에 크롬북에서 무겁다. 2.5D 도형 엔진으로는 Isomer, Obelisk.js가 있지만 그림만 그리는 도구이고 데이터 바인딩, 인터랙션, 접근성 기능이 없다.

그래서 새 브라우저나 렌더링 엔진을 만들지 않는다. 크롬에 이미 최적화되어 있는 2D 래스터 파이프라인 위에 등각 투영 공식을 CSS로 올리는 방식을 택한다.

원칙

설계 원칙

  • 투영은 고정한다. 화면 좌표는 X = (x − y)·0.866, Y = (x + y)·0.5 − z로만 계산한다. 삼각함수와 프레임마다 하는 깊이 정렬이 없다.
  • 2D 변환만 쓴다. 각 면은 matrix() 하나로 그린다. preserve-3d는 쓰지 않아 합성 레이어가 늘지 않는다.
  • 음영은 3단 고정이다. 윗면은 기본색, 왼쪽 면은 18%, 오른쪽 면은 34% 어둡게 color-mix(in oklch)로 만든다. 색 하나(--c)만 바꾸면 블록 전체가 바뀐다.
  • 쉴 때는 CPU를 쓰지 않는다. 렌더 루프가 없다. 값이 바뀔 때만 CSS 트랜지션이 돌고 멈춘다.
  • 텍스트는 DOM으로 둔다. 값과 라벨은 기울이지 않은 일반 텍스트다. 데이터 그림마다 숨김 표나 aria 설명을 붙인다.
  • 선언형으로 사용한다. 사용자가 기하 계산을 하지 않는다. <iso-bars data="…">나 style="--h:3" 수준에서 끝낸다.
P0 비교 대상

렌더링 방식 후보

P0 측정 결과(docs/adr/0001-render-approach.md)로 A안을 기본으로 확정했다. 블록 500개까지는 A안의 호버 프레임 드랍이 0%였지만, 1000개에서는 52%였다. 그래서 500개를 넘으면 C안(SVG)으로 전환한다. C안은 1000개에서 0.8%, 2000개에서 8.1%였다. 측정은 데스크톱에서 CPU를 6배 느리게 해서 했고, 크롬북 실기기 확인이 남아 있다.

구성

컴포넌트 로드맵

프리미티브 (CSS만)

  • .iso-scene: 단위 크기(--u)와 원점을 정하는 컨테이너
  • .iso-block: --x --y --w --d --h --c로 정의하는 직육면체
  • .iso-floor, .iso-grid: 바닥판과 격자선
  • .iso-label: 윗면 중심이나 바닥 모서리에 붙는 기울이지 않은 라벨

데이터 컴포넌트

  • 막대(DataTower): 값에 비례한 높이, 최댓값 기준 축척, 강조 색
  • 적층 막대: 한 기둥 안에 여러 계열을 쌓음(용량, 비용 구성)
  • 등각 히트맵: 행 × 열 격자의 셀 높이로 세 번째 변수를 표현
  • 적층 원장: 버전·이력을 종이 묶음처럼 쌓고, 선택한 시점을 앞으로 빼냄
  • 볼륨 KPI 박스: 한 지표를 채움 높이로 보여 주는 카드

템플릿

  • 리소스 사용 대시보드, KPI 보드, 버전 이력 뷰어

패키지 구성

  • packages/core: 코어 CSS와 Web Components. 프레임워크 의존성 없음
  • packages/react: IsoBars, IsoStack, IsoHeatmap, IsoLedger, IsoKpi React 컴포넌트와 타입

사용 형태는 세 가지이며 모두 같은 CSS 위에서 동작한다.

<!-- CSS만 -->
<div class="iso-scene">
  <div class="iso-block" style="--x:0; --h:3.2; --c:var(--iso-blue)">…</div>
</div>

<!-- 선택형 JS: 데이터만 전달 -->
<iso-bars max="500" data='[{"k":"문서","v":180},{"k":"화상회의","v":410}]'></iso-bars>

// React 래퍼(별도 패키지)
<IsoBars max={500} data={[{ k: "문서", v: 180 }, { k: "화상회의", v: 410 }]} />
일정

단계별 계획

기간은 1인 기준 추정치다. 단계마다 완료 조건(AC)을 모두 통과해야 다음 단계로 넘어간다.

  1. P0

    검증 스파이크

    1주

    A–D안을 같은 데이터(블록 50, 500, 2000개)로 구현하고 성능 예산 항목을 측정한다. 대화에서 나온 선행 사례 주장도 이때 확인한다.

    AC-P0-1방식별 측정표 작성 AC-P0-2기본 렌더링 방식 확정을 ADR로 기록

  2. P1

    코어 CSS

    2주

    프리미티브 4종, 색 토큰과 3단 음영, 다크 테마, @property로 등록한 --h 트랜지션, prefers-reduced-motion 대응을 만든다.

    AC-P1-1코어 CSS ≤ 6 KB gzip AC-P1-2시각 회귀 스냅샷 통과(라이트·다크·모바일)

  3. P2

    데이터 컴포넌트

    3주

    막대, 적층, 히트맵, 원장, KPI 박스를 만들고 축척, 라벨 충돌 회피, 접근성 표 자동 생성을 넣는다.

    AC-P2-1컴포넌트마다 스크린 리더로 값 전체 낭독 확인 AC-P2-2블록 500개 첫 렌더 ≤ 100 ms

  4. P3

    Web Components와 React 래퍼

    2주

    <iso-bars> 등 커스텀 엘리먼트를 만든다. 값이 바뀐 블록만 다시 계산한다. 별도 패키지 packages/react에 타입이 있는 React 컴포넌트를 만든다.

    AC-P3-1코어 JS ≤ 4 KB gzip AC-P3-2유휴 CPU 0% 트레이스 첨부 AC-P3-3React 18/19 props 반영 테스트 통과

  5. P4

    문서와 플레이그라운드

    1–2주

    컴포넌트별 예제, 속성 표, 실시간 편집 페이지와 템플릿 3종을 만든다.

    AC-P4-1모든 예제가 크롬북 실기기에서 동작

  6. P5

    v0.1 공개

    1주

    npm 패키지와 CDN 단일 CSS 파일로 배포하고 라이선스와 변경 기록을 정리한다.

    AC-P5-1CDN 한 줄로 데모 재현 AC-P5-2CI 3단계 검증 통과

확인 결과

참고 대화 사실 확인

계획의 근거로 쓴 Gemini 대화의 주장을 P0에서 확인했다. 출처는 ADR 0001 부록에 있다.

  • PolyCSS: 실재하고 유지보수 중이다. 메시 렌더러이며 데이터 컴포넌트는 아니다
  • City4Age: 사실이 아니다. 노인 돌봄 분야의 EU 연구 프로젝트다. 코드 시티 사례는 Wettel의 CodeCity다
  • WebGL 캔버스 하나에 80–200MB: 근거를 찾지 못했다. 컨텍스트 고정 오버헤드는 수 MB 수준이라 논거에서 뺐다
  • Isomer, Obelisk.js: 유지보수가 중단됐다(마지막 커밋 2017년, 2019년). 데이터 바인딩형 비-WebGL 2.5D 컴포넌트 라이브러리는 찾지 못했다
  • Tailwind CSS v4: 3D 변환 유틸리티가 있다. 모두 preserve-3d 계열이라 기각한 B안에 해당한다

결정 사항 2026-10-04 확정

  • 클래스·커스텀 속성 접두사는 iso- / --iso-로 한다
  • 라이선스는 MIT로 한다
  • React 래퍼는 별도 패키지(packages/react)로 제공하고, 코어는 React에 의존하지 않는다
  • npm 패키지 이름은 v0.1 공개 단계(P5)에서 확정한다
